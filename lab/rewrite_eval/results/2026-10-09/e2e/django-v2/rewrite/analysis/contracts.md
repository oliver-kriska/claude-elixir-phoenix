Stack in force: Django 1.10.5, DRF 3.4.4, PyJWT 1.4.2, django-cors-middleware 1.3.1, SQLite (`requirements.txt`, `conduit/settings.py`).
**There are no legacy tests.** The repo has no test files, so the `Legacy test` column is `—` in every row. The external
consumer evidence is the published RealWorld API spec that the README says this app adheres to (`README.md:3`).
Behaviour marked *(lib)* comes from reading the library's code paths for these pinned versions. Nothing was executed.
Every witness below is a probe the port's test suite must run. Where a witness pins legacy behaviour, run it once against a
disposable legacy instance before freezing it (Iron Law 10: that needs an isolation decision).

## Data Schema Notes

DDL comes from the Django 1.10 SQLite backend *(lib)*: AutoField `integer NOT NULL PRIMARY KEY AUTOINCREMENT`,
CharField `varchar(n)`, TextField `text`, DateTimeField `datetime` (text, naive UTC), BooleanField `bool` (0/1),
FK `integer … REFERENCES` plus an index. **Foreign keys are declared but not enforced.** Django enabled
`PRAGMA foreign_keys` on SQLite only from 2.2 *(lib)*, and CASCADE ran in Python. Expect orphan rows in a legacy DB
and run an orphan scan before import.

- `authentication_user` — id; password varchar(128) (`pbkdf2_sha256$30000$…`); last_login datetime NULL (effectively always NULL for API users); is_superuser bool; username varchar(255) UNIQUE; email varchar(254) UNIQUE (case-sensitive; domain lowercased on create); is_active bool default true (the soft-deactivate flag; the comment in models.py:68-73 says users are deactivated rather than deleted, but no endpoint deactivates); is_staff bool; created_at, updated_at datetime NOT NULL.
- `profiles_profile` — id; user_id UNIQUE FK; bio text NOT NULL (`''`); image varchar(200) NOT NULL (`''`; URL not validated on the API path); created_at, updated_at.
- `profiles_profile_follows` — id; from_profile_id, to_profile_id; UNIQUE(from, to). Directed: from follows to (`symmetrical=False`). May contain self-follows (C-38).
- `profiles_profile_favorites` — id; profile_id, article_id; UNIQUE pair.
- `articles_article` — id; slug varchar(255) UNIQUE; title varchar(255) indexed; description text NOT NULL; body text NOT NULL; author_id FK → profiles_profile (**the author is a profile, not a user**); created_at, updated_at.
- `articles_comment` — id; body text; article_id FK; author_id FK → profiles_profile; created_at, updated_at.
- `articles_tag` — id; tag varchar(255) (not unique); slug varchar(50) UNIQUE (= lower(tag); may be longer than 50 in SQLite, C-07); created_at, updated_at.
- `articles_article_tags` — id; article_id, tag_id; UNIQUE pair.
- No enums, JSON columns, serialized blobs, encrypted columns, polymorphic/STI columns, triggers, views or FTS tables. Soft delete is limited to `is_active`.
- Model ordering `-created_at,-updated_at` is ORM-level (no DB index on created_at). It drives every list.
- Migrations appear to match the models (no `makemigrations` drift was visible by reading; not executed).

## Decisions Needed for ADR-000

1. **C-14 leaked `SECRET_KEY` + C-11 token survival (Q3).** Either rotate the key, which logs out every client once (tokens expire within 60 days anyway) and closes the forgery hole, or reuse the committed key for a coexistence window and accept forgeable tokens in an AR record. Keeping it is a security departure.
2. **C-32 / C-33 authz bypasses.** Enforce author-only article update and comment delete, scoped to the article. This tightens behaviour, and only attackers lose access, but it is still a guarantee change that needs approval.
3. **C-34 DEBUG pages.** Retire them; the port returns JSON or minimal errors.
4. **Error and status contract (C-16, C-25, C-26).** Option A: keep legacy DRF quirks byte-for-byte (400 validation, 403 auth, label-wrapped `detail`, mixed NotFound shapes, 201 on favorite and follow, `{"errors":[…]}` list for self-follow). Option B: conform to the RealWorld spec (422, 401, uniform `{"errors":{"body":[…]}}`). Option B removes a compat adapter but changes behaviour for clients coded against this backend. This choice decides whether a `Conduit.Compat` error/JSON adapter exists.
5. **Spec-gap defects (C-35 feed shadowing, C-36 article DELETE, C-37 password/image update, C-40 user bio/image, C-23 comment pagination at 20).** Decide fix-to-spec (redesign) or preserve, one by one. Fixing all of them makes the port match the spec the README claims.
6. **Trailing slashes (C-17).** Phoenix matches both forms by default. Decide whether accepting `/api/articles/` (legacy: HTML 404) is acceptable widening.
7. **Data carry-over (Q2, with infra Q1).** Import an existing `db.sqlite3` or start empty, and choose the target DB (SQLite vs Postgres). If importing: PBKDF2 verify plus a rehash policy (C-02), the timestamp text format (C-03), oversize tag slugs (C-07), the orphan scan, the self-follow scan (C-38) and case-variant email duplicates (C-04).
8. **Email and username case policy (C-04, C-39).** Keep case-sensitive exact matching, or move to case-insensitive matching (citext or a lower index) after a duplicate scan. Restrict the username charset, or make profile routes accept any username.
9. **Revocation strength (C-12).** Keep stateless 60-day tokens with no logout or password-change revocation, or strengthen it (DB token table, `phx.gen.auth` UserToken). A stronger design changes client-visible logout behaviour.
10. **Django admin and createsuperuser (C-52, C-43).** Retire them, or provide an operator replacement (release eval task to create a user).
11. **CORS origins (C-31).** Keep `:4000` origins as runtime-configurable defaults, or require explicit configuration.
