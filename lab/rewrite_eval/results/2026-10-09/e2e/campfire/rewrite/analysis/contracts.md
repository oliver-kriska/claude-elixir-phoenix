## Data Schema Notes

- **Primary keys**: SQLite `INTEGER PRIMARY KEY` everywhere (Rails bigint). Several FK columns are `integer` while `rooms.creator_id` and `*_record_id` are `bigint`: same storage in SQLite.
- **No DB-level FK** from `memberships`, `rooms.creator_id`, `boosts.booster_id` to `users`/`rooms`; orphans are possible. The FKs that exist: attachments→blobs, variant_records→blobs, bans/push_subscriptions/searches/sessions/webhooks→users, boosts→messages, messages→rooms, messages.creator_id→users.
- **Timestamps**: `t.datetime` is precision 6 under Rails 7+; zone is UTC (no `config.time_zone`). `Time::DATE_FORMATS[:epoch]` exposes ms timestamps to JS (`data-message-timestamp`, `refresh?since=`).
- **Enums**: integer `role`, `status`; string `involvement`; STI `rooms.type`. `role=2` meant "owner" before migration 20240115124901 and was remapped to administrator; today `2` means bot. Any install skipping that migration would turn owners into bots: the auto-migrate path (C-55) must run it.
- **Users**: `password_digest` nullable (bots); `email_address` nullable (bots), unique, case-sensitive, no normalization in the model; `bot_token` 12 alphanumeric.
- **Messages**: no `body` column. The body is `action_text_rich_texts.body` (HTML) for `record_type='Message', name='body'`; attachment via `active_storage_attachments(name='attachment')`. `client_message_id` NOT NULL, client-supplied or random UUID. `content_type` (attachment / sound `/play <name>` / text) is derived, not stored.
- **FTS5**: `message_search_index` is a virtual table created by raw SQL; `db/schema.rb` records it with `create_virtual_table`. Ecto `structure` dumps must keep it. Index rows exist only for messages created through the app; no triggers.
- **JSON columns**: `accounts.settings` (`t.json` → TEXT in SQLite, read through Rails 8.2 `has_json` with defaults); `active_storage_blobs.metadata` (TEXT JSON).
- **Serialized or Marshal data**: none in columns. Marshal appears only inside old Rails 7 sgids embedded in rich-text HTML (C-10) and in Active Storage's variation digest computation (variant records). The port should never unmarshal; the legacy code extracts the GID string by regex.
- **Encrypted columns**: none (`encrypts` not used). Secrets at rest: `users.bot_token` and `sessions.token` stored in plaintext; `webhooks.url` may embed credentials.
- **Soft delete**: none. Deactivation and ban use `users.status` plus email rewriting; banned users' messages are destroyed asynchronously.
- **Singletons**: `Current.account = Account.first`; first run creates the account "Campfire", room "All Talk" (open) and the admin.
- **Derived counters**: `memberships.connections` and `connected_at` (presence TTL 60 s), reset by `Membership.disconnect_all` at boot; `memberships.unread_at`.

## Decisions Needed for ADR-000

1. **Cutover mode for existing installs.** In-place upgrade on the same `/rails/storage` volume with the same image name and auto-migration (C-01, C-50, C-55), versus a one-time import tool. ONCE auto-update makes in-place the default expectation; an import path changes the operator contract.
2. **Rollback window and migration ownership.** Must the pinned Rails image still boot on a DB the port has written (C-01, C-02, C-09, C-13)? This decides whether the port may change the schema at all, whether FTS stays app-maintained or moves to triggers both apps share, and how long `schema_migrations` stays authoritative.
3. **Session continuity.** Honor the legacy `session_token` signed cookie through a one-way reader over the existing `sessions` table (C-20, C-08), versus forced re-login of every user on every install. The cookie is signed, not encrypted, and the DB row is the authority, so the reader is narrow; the digest and key-derivation parameters still need vectors from the pinned image.
4. **`SECRET_KEY_BASE` reuse and which signed capabilities stay valid.** Avatar tokens (no expiry, C-23), blob URLs (no expiry, C-27), transfer links (4 h, C-24), mention sgids in stored HTML (C-10). Keep narrow per-purpose verifiers, redirect, or accept breakage.
5. **Bot API and webhook compatibility.** Keep byte-compatible (key in path, raw body, headers, JSON shapes, reply semantics, no signature, no retry) (C-30 to C-36), or version the API. This is a charter-assumed must-keep integration.
6. **Rich-text storage format.** Keep Action Text HTML with `<action-text-attachment>`/sgid (and the legacy Trix and Rails 7 forms) as the canonical body (C-10), or migrate bodies to a new format with a backfill.
7. **Active Storage layout.** Keep `active_storage_*` tables, disk layout, variant records and public unauthenticated download URLs (C-11, C-27), or change the file contract. Making downloads require a session is a guarantee change that needs explicit approval.
8. **Realtime and UI protocol.** Retire Action Cable and the Turbo stream protocol with a LiveView UI (C-41, C-48, C-49: only open tabs affected), or keep the Hotwire frontend and run a cable-compatible shim.
9. **Web Push continuity.** Keep VAPID keys, subscription rows, payload shape and SW URL (C-15, C-37, C-39), or require users to re-enable notifications.
10. **Operator surface.** Keep env var names, admin script paths and outputs, ONCE hooks, ports, uid 1000 and TLS behavior (C-50 to C-57), or publish a migration guide for self-hosters.
11. **Redis removal.** Since Redis is non-persistent today (C-59), confirm that dropping Redis/Resque with no job drain is acceptable and that no external `REDIS_URL` users depend on it.

## Questions

1. Exact crypto parameters under `load_defaults 8.2`: key-generator hash (SHA1 vs SHA256), signed-cookie HMAC digest, message serializer, and the `signed_id` and `signed_global_ids` verifier secrets. `test/performance/create_dummy_cookies.rb` shows SHA1 HMAC, 1000 iterations and salt `signed cookie`, but the app's `key_generator_hash_digest_class` may differ. Generate known-answer vectors in the pinned image before writing any reader.
2. Does Lexxy persist the mention's rendered `content` (including `/users/<avatar_token>/avatar` URLs) inside `action_text_rich_texts.body`? This decides whether avatar tokens are durable data or only transient HTML. Check on a production-shaped copy.
3. The webhook reply quirk: a non-200 response with a recognized content type (for example a 500 `text/html` error page) is posted to the room as an attachment, because `extract_attachment_from` does not check the status. Is this a contract bot authors rely on, or a bug to fix with approval?
4. Which oldest released version must upgrade directly to the port? Migrations back to 2023-12 exist, including the owner→administrator remap.
5. Are there known external API consumers beyond curl-style bots (mobile apps, Basecamp integrations)? None were found in the repo.
6. Where does Thruster keep its ACME certificates (`/rails/storage/thruster` is assumed)? Does the port need to reuse them to avoid Let's Encrypt rate limits on mass upgrade?
7. Is `config/purchased_by.yml` still shipped to paying customers, and must the port honor it?
8. `remote_ip` behind Thruster or a user's proxy decides bans and rate limits. What trusted-proxy configuration must the port match?
9. Bot key comparison is a plain SQL equality on `bot_token` (not constant-time). Must the port preserve or tighten this?
